TalentGuard — Implementation Blueprint
Antigravity project context · Version 1.0 · P0 MVP
This specification defines the implementation contract for TalentGuard: Retention Command Center. It preserves the selected solution: an explainable attrition-risk model, a capacity-constrained Top-50 employee ranking, three evidence-backed risk reasons per employee, three rule-based recommendations for each Top-10 employee, and persistent HR review decisions.
Architecture decision: Build one React application, one FastAPI application and one Supabase project. Use scikit-learn for the ML pipeline. No LLM, microservices, background queue or paid API is required.
1. Product specification
1.1 Problem and users
TechNova Solutions is assumed to have 12,000 employees, an annual attrition rate of 10%, and capacity to conduct retention sessions with 50 employees per cycle.
The IBM HR Analytics dataset contains 1,470 historical employee records. It is a demonstration dataset, not TechNova's real employee directory.
Primary user: HR Manager.
Product objective: identify the 50 highest-ranked employees by predicted attrition probability, explain the model evidence, suggest retention actions for the Top 10, and let HR record review decisions.
1.2 P0 features and acceptance criteria
ID	Feature	Acceptance criteria
P0-01	Authentication	An authenticated HR user can access protected pages; unauthenticated requests receive 401.
P0-02	Dataset validation	The pipeline validates required columns and target values, reports row counts and rejects malformed datasets with actionable errors.
P0-03	Model evaluation	A reproducible Logistic Regression baseline returns ROC-AUC, average precision, and documented evaluation metadata.
P0-04	Top-50 ranking	The system returns up to 50 eligible employees in descending risk order. When at least 50 eligible employees exist, it returns exactly 50.
P0-05	Risk explanations	Each ranked employee has three readable, model-derived feature contributions with observed values and contribution direction.
P0-06	Top-10 recommendations	The first 10 ranked employees each receive three applicable recommendations generated from explicit rules.
P0-07	HR review	HR can save and retrieve a review status and optional note for a ranked employee.
P0-08	Dashboard	The dashboard displays the latest run, dataset summary, model metrics and Top-50 count using real API data.
P0-09	Persistence	Model runs, rankings, explanations, recommendations and HR reviews survive page reloads.
P0-10	Security	No service-role key is exposed to the browser. The backend verifies the user's identity and authorizes every protected operation.
1.3 User stories
- As an HR Manager, I want to see model quality before relying on the rankings.
- As an HR Manager, I want the Top 50 sorted by risk so I can prioritize limited retention capacity.
- As an HR Manager, I want to understand the three strongest risk signals for an employee.
- As an HR Manager, I want practical retention suggestions for the Top 10.
- As an HR Manager, I want to record a review decision and retrieve it later.
1.4 Primary user journey
1. Sign in.
2. Open the dashboard.
3. Open Model Lab and start a run using the supplied dataset.
4. Review validation results and evaluation metrics.
5. Open the Top-50 ranking.
6. Select an employee and inspect the risk evidence.
7. For a Top-10 employee, review three recommendations.
8. Record a review status and note.
9. Refresh the page and confirm that the review is still present.
1.5 Explicitly out of scope
- LLM-generated recommendations or chatbots.
- Automated email, Slack or HRMS integration.
- Simulated or guaranteed retention savings.
- Real-time HR data synchronization.
- Multiple ML models, hyperparameter optimization or deep learning.
- Multi-tenant enterprise administration and complex role hierarchies.
- Employee self-service, manager portals and automated employment decisions.
- Advanced audit analytics and historical model comparisons.

3. Backend specification
3.1 API routes
Base prefix: /api/v1.
Method	Endpoint	Responsibility
GET	/health	Return service health
GET	/auth/me	Return identity and authorized role from verified token
POST	/runs	Validate dataset, train/evaluate model, score and persist a run
GET	/runs	List the authenticated user's accessible runs
GET	/runs/{run_id}	Return run metadata, metrics and validation summary

3.3 ML responsibilities
The backend pipeline should:
1. Validate the required columns and target values.
2. Remove identifier and constant columns.
3. Exclude the target from all predictors.
4. Use a scikit-learn preprocessing pipeline with train-only fitting.
5. Train Logistic Regression with class_weight="balanced".
6. Evaluate on a stratified held-out set.
7. Calculate ROC-AUC and average precision; calculate Precision@50 and Recall@50 with explicitly defined denominators.
8. Generate the final eligible scoring population and rank its probabilities.
9. Select the Top 50.
10. Calculate the three strongest feature contributions per selected employee.
11. Apply deterministic rules to create Top-10 recommendations.
12. Persist run metadata and ranking records.
Important evaluation distinction: Metrics must be computed against held-out labels, not the data used to fit the model. Precision@50 and Recall@50 must be calculated using a defined held-out ranking cohort. They are not automatically the same as metrics for the final full-dataset Top 50.
For a genuine next-cycle prediction, a time-aware split is preferable when suitable dates and future outcomes exist. The supplied dataset may not support that design, so the MVP should disclose its limitations.
3.4 Validation and error handling
Use Pydantic schemas and FastAPI validation. Return consistent error responses:
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The dataset is missing required columns.",
    "details": {
      "missing_columns": ["Attrition"]
    },
    "request_id": "req-123"
  }
}


Recommended HTTP status mapping:
Status	Meaning
400	Invalid operation or dataset state
401	Missing or invalid authentication
403	Authenticated but unauthorized
404	Resource not found or not accessible
409	Conflicting state or duplicate operation
422	Invalid request fields
500	Unexpected server failure
The actual dataset column names and target categories must be validated, not silently renamed or inferred. Log diagnostic details server-side without logging credentials or sensitive employee records.
3.5 External dependencies
Required Python packages: FastAPI, Uvicorn, Pydantic, pandas, scikit-learn, Supabase Python client or an equivalent supported PostgreSQL access layer, and an HTTP client if needed for token verification.
No LLM provider, paid API, Redis, Celery or external HR platform is required.

4.2 Relationships and indexes
- profiles 1 → many model_runs.
- model_runs 1 → many employee_risks.
- employee_risks 1 → zero or one hr_reviews.
- profiles 1 → many hr_reviews.
Indexes:
- model_runs(created_by, created_at DESC)
- employee_risks(run_id, risk_rank)
- employee_risks(run_id, risk_probability DESC)
- hr_reviews(reviewer_id, updated_at DESC)
Avoid indexing every JSON field. Add further indexes only when queries require them.
4.3 Ownership and RLS
For the MVP, each authenticated HR user owns their own runs and reviews. This is the default ownership model, not a claim that the eventual organization must isolate all HR data per user.
Enable RLS on all tables accessible through the Supabase Data API.
- profiles: users can read their own profile; users cannot grant themselves elevated roles.
- model_runs: owners can read their own runs; inserts and updates must bind ownership to the verified identity.
- employee_risks: access is allowed only when the parent run belongs to the user.
- hr_reviews: users can read and modify only reviews they own, and only for employee risk records belonging to their accessible runs.
If only FastAPI accesses PostgreSQL, use a backend-only database connection with verified user identity and explicit ownership filters. Do not assume RLS is automatically enforced when using a privileged service-role connection. Where service-role access is used, the backend must enforce authorization itself.
For the simplest secure design, expose only necessary database access through FastAPI, use least-privilege access where feasible, and test unauthorized cross-user access explicitly.
4.4 Seed and demo data
Required:
- The official IBM HR CSV in a controlled backend data directory.
- One authenticated demo HR account created through Supabase Auth.
- A profile associated with that account.
- One completed model run and its Top-50 results for deployment demonstration, generated by the real pipeline.
Do not seed invented employee risk probabilities or fake model metrics. A demo run may be generated during setup or by the first authenticated user. If pre-generated records are used, preserve their actual model configuration and evaluation results.
4.5 Storage
Supabase Storage is optional for P0. The bundled dataset does not require a storage bucket.
If CSV uploads are added later, create a private bucket such as hr-datasets. Allow access only to authorized HR users; validate file size, extension, content and schema on the backend. Never trust a client-provided storage path as proof of ownership.

6. Integration contract
6.1 API and authentication
API prefix
/api/v1


Request format
JSON


Authentication
Supabase JWT bearer token


Error format
Standard error object


The authentication flow is:
1. The user signs in through Supabase Auth in React.
2. Supabase provides an access token.
3. The API client sends Authorization: Bearer <access_token>.
4. FastAPI verifies the token using a supported Supabase JWT verification method.
5. The backend derives the authenticated user ID from the verified token.
6. Every database operation checks ownership and authorization before returning or changing data.
The backend must not trust a user ID supplied in request bodies, query parameters or arbitrary headers.

Configuration rules:
- SUPABASE_SERVICE_ROLE_KEY is optional if the selected persistence implementation does not require it. Never expose it through VITE_*.
- If using direct PostgreSQL access, configure a separate backend-only database connection string instead of requiring the service-role key.
- Confirm the actual JWT issuer and verification configuration from the Supabase project settings; do not assume all project configurations use identical signing keys.
- Never commit real .env files.
- Validate required settings at application startup and fail with a clear configuration error.
6.3 CORS
Allow only explicitly configured frontend origins, such as:
- http://localhost:5173 during local development.
- The deployed frontend's actual HTTPS origin in production.
Allow required methods (GET, POST, PUT, OPTIONS) and headers (Authorization, Content-Type). Do not use unrestricted wildcard origins with credentialed requests.
6.4 Contract consistency rules
- Use UUID strings for run IDs and employee risk record IDs.
- Use risk_probability as a number from 0 to 1.
- Use risk_rank as a positive integer.
- Use employee_risk_id consistently for employee detail and review updates.
- Use the exact four defined review statuses everywhere.
- Use ISO 8601 UTC timestamps.
- Use snake_case for all API fields and database columns.
- Use the same error response schema for all handled API errors.
- Ensure that a successful review update is confirmed by the server before the UI shows success.

7. Implementation plan
Build in dependency order. The frontend and backend can be developed in parallel after the API and database contracts have been agreed.

Phase 3
Database and authentication
Files: 001_initial_schema.sql, config.py, auth.py, dependencies.py, lib/supabase.js.
Deliverables: Tables, constraints, indexes, RLS policies, login integration and protected backend dependencies.
Definition of done: Authorized users can sign in; unauthorized users cannot access protected records.
Manual verification: Test sign-in/sign-out, expired tokens, unauthenticated API requests and cross-user access restrictions.



Phase 4
ML and backend APIs
Files: schemas.py, routers/, dataset_service.py, model_service.py, explanation_service.py, recommendation_service.py, persistence_service.py.
Deliverables: Dataset validation, model evaluation, Top-50 scoring, three explanations, Top-10 recommendations and persistent model runs.
Definition of done: A real dataset run produces valid metrics, correctly ordered records and structured explanations without hardcoded prediction values.
Manual verification: Inspect the dropped columns, verify the train/test split, check positive-class metrics, inspect three real feature contributions and confirm that ranking order is descending.



Phase 5
Frontend/backend integration
Files: apiClient.js, runService.js, priorityService.js, reviewService.js, dashboard and employee page components.
Deliverables: Replace fixtures with real API calls and wire review updates to persistence.
Definition of done: The user can complete the entire P0 journey using actual model results.
Manual verification: Create a run, inspect Top 50, open a Top-10 employee, save a review and refresh the page to verify persistence.



Phase 6
Testing and stabilization
Files: backend/tests/, frontend components and service modules as required.
Deliverables: Tests for dataset validation, metrics, ranking, explanations, recommendation rules, API validation and review authorization.
Definition of done: The core workflow passes from a clean session with no fabricated values or lost review updates.
Manual verification: Test malformed data, missing columns, invalid tokens, empty results, API failures, repeated review updates and Top-50 count constraints.



Phase 7
Deployment and demo
Files: Hosting configuration, production environment settings and README.md.
Deliverables: Deployed frontend, deployed backend, configured Supabase project and reproducible demo dataset/run.
Definition of done: The deployed application authenticates, loads rankings, retrieves employee evidence and persists HR decisions.
Manual verification: Test using a clean browser session, verify CORS and HTTPS, confirm secrets are absent from the frontend bundle and rehearse the three-minute demonstration.
